# 爆点逃跑 —— 算法与赔率引擎

> 本文面向后续维护者。假设你没见过这个项目，只知道它是一个 Discord 上的
> crash 类小游戏：10 秒下注 → 5 秒封盘 → 火箭起飞，倍率持续上涨，玩家随时可以
> 点「逃跑」按当前倍率结算，倍率涨到某个值就爆炸，本局结束。玩家赢的钱是
> `倍率 × 投入`。
>
> 本文只讲**赔率算法与飞行曲线**这一层。前端、Discord 对接、经济活动不在此列。
> 文中所有数字都来自对生产引擎的实测，样本量写在旁边。

---

## 0. 先建立直觉：为什么这个项目的赔率引擎是纯概率的

早期版本的赔率会参考「当前资金池」「上一局爆点」「房间里坐着几个人」来决定本局
倍率。这个设计有一个致命问题：**房间状况不变，分布就不变**。玩家只要观察到
「这个点人少的时候倍率总在 1.3 附近」，就可以固定在 1.3 逃跑长期获利。每一代
算法都栽在这里——均匀分布、五段加权、Jev 选段、池子反推，根子都一样。

现在的引擎只有一个分支，**爆点只由一个均匀随机数决定**：

```js
X = min(cap, max(1.00, floor(RTP / U)))     // U ~ Uniform(0,1)
```

其中 `RTP` 是返还率（可运营配置），`cap` 是倍率上限。没有任何其它输入。

理解这个设计的代价很低，但收益是**根本性的**：不存在「房间不变所以分布不变」
这类可利用结构。下面所有验收标准都是为了守住这一点。

## 1. 幂律引擎的数学原理

### 1.1 一个反直觉但关键的事实

玩家固定在 `m` 倍逃跑，长期期望收益是：

```
EV(m) = P(赢) × (毛赔付 − 投入) + P(输) × (−投入)
```

玩家赢的条件是「爆点 ≥ m」。所以毛返还 = `m × P(X ≥ m)`。注意这里最容易
写错——**不能只算赢的那一支**：

```
错： EV(m) = P(赢) × (毛赔付 − 1)        → 会得出「逃得越高越好」的错误结论
对： EV(m) = P(赢) × (毛赔付 − 1) + (1 − P(赢)) × (−1)
```

补上输掉那一支后，设 `S(m) = P(X ≥ m)`（生存函数，survival function）：

```
EV(m) = S(m)·m − S(m) + (1 − S(m))·(−1) = S(m)·m − 1
```

代入 `S(m) = RTP/m`：

```
EV(m) = RTP − 1
```

**`m` 整个约掉了。** 无论玩家选哪个逃跑点，长期期望都是同一个数。

再扣掉平台抽水（`HOUSE_EDGE = 0.03`，写死在 `payout()` 里，与后台的
`rake_percent` 设置无关）：

```
玩家每注净 EV = 0.97 × RTP − 1
```

这就是 FAQ 里「没有更好的逃跑点」的**数学依据**。它不是一个平衡出来的数值，
而是一条恒等式：将来把 RTP 改成 0.80 还是 1.00，它都成立，运营文案可以长期挂着
而不会被拆穿。

### 1.2 闭式解怎么来的

原版 PHP 是用循环逼近的：不断 `t += 0.04` 直到倍率公式的输出超过目标倍率，
再把 `t` 换算成毫秒。这个循环有两个问题：慢，且 `t` 是离散步长所以有量化误差。

把倍率公式反解就得到闭式解。倍率随时间的曲线是：

```
rate(t) = t/2 + (t² − t)/10 + 1
```

要求 `rate(t) = r`，即解一个关于 `t` 的二次方程：

```
r = t²/10 + t·(1/2 − 1/10) + 1
  = t²/10 + 2t/5 + 1
0 = t² + 4t + 10(1 − r)
t = [−4 ± √(16 − 40(1−r))] / 2 = [−4 ± √(40r − 24)] / 2
```

`t ≥ 0` 时取正号：

```js
t = (Math.sqrt(40 * r - 24) - 4) / 2
```

**时间缩放系数 2.5 是必须的。** 原版 PHP 是
`usleep(($t / 0.04) * 100 * 1000)` 微秒。化简：`(t/0.04) = t×25`，
`t×25×100×1000 = t×2,500,000` 微秒 = **t × 2.5 秒**。用 `t × 1` 秒会只剩原版
窗口的 40%，1.10x 只有 0.24 秒，玩家物理上按不到逃跑键，界面看起来就像按钮坏了。

这个缩放必须**在三个地方一致**：服务端的 `flightMs()`、客户端 `tick()` 里推算
倍率的 `t` 推导、以及 `/api/me` 播出的 `flightScale`。任一处不一致，屏幕显示的
倍率就会和实际结算的倍率脱钩。

实测往返精度（`flightMs(r) → rateAt(ms)`）：

```
1x     →      0ms → 1.000000x     误差 0
2x     →   4354ms → 1.999957x     误差 4.29e-5
10x    →  19238ms → 9.999690x     误差 3.10e-4
100x   →  73819ms → 99.998956x    误差 1.04e-3
1000x  → 100000ms → 1000.000090x  误差 9.00e-5
```

### 1.3 高倍加速：曲线必须在 100x 处连续

`flightMs(1000)` 在原速下是 700 秒。一局飞 11 分钟会把整个游戏卡死。

但**不能简单地把飞行时长钳制（clamp）到某个上限**——钳制意味着屏幕显示
「1000x」而实际只飞了 120 秒，**读起来就是一个被做局的游戏**。

正确做法是**把曲线压扁**而不是钳制时长。对 `rate ≥ 100` 的部分做**对数线性**
变换：每「翻一倍倍率」所增加的时长是同一个常数。

```
100x  →  73.8s   （= ACCEL_FROM 处的原速，与未加速曲线无缝衔接）
200x  →  81.7s   (+7.9s)
400x  →  89.6s   (+7.9s)
800x  →  97.5s   (+7.9s)
1000x → 100.0s
```

**为什么是对数线性、不是「越往后越快」：** 「越快」意味着时长随倍率**下降**
（1000x 飞 24.5 秒而 100x 飞 73.8 秒）。玩家一眼就能从「飞得特别快」认出千倍局，
这和「某个固定倍率有特殊待遇」是同一类缺陷。对数线性保证时长**严格单调递增**，
只是斜率递减。

实现上有一个必须避开的陷阱：**共享常量必须在模块加载时算一次**。如果写成
惰性自举（`fn.base ??= ...`），`flightMs()` 和它的逆函数 `rateAt()` 可能各自
初始化、各自持有不同的 base，实测往返误差可达 **99.9%**（1000x 被反解成
1857x）——屏幕显示一个倍率、按另一个倍率赔付。

判别阈值用 `>=` 而不是 `>`：在 `ACCEL_BASE_MS` 处加成为恒等变换，两个分支
都得同一个值，否则 `100.00x` 与 `100.01x` 会差出整整 73 秒的断崖。

### 1.4 四个必须照抄的构造细节

#### ① 随机源必须是 CSPRNG

```js
const b = crypto.randomBytes(6);           // 48 bit
```

`Math.random()` **不可用**。V8 的实现是 xorshift128+，内部状态只有 128 bit，
观察到连续输出就足以恢复状态并预测后续所有「随机」数。对一个直接决定金钱的
游戏来说，这意味着爆点可被预测。

验收要求：`powerlawRate()` 在一轮采样中调用 `Math.random()` 的次数必须**恰好
为 0**（用打桩计数断言，不靠读代码）。

#### ② 截断必须用 clamp，不能用「超界重抽」

`U` 接近 0 时 `RTP/U` 会超过 `cap`。两种处理方式：

| 方式 | 实现 | 后果 |
|---|---|---|
| **clamp**（采用） | `min(cap, ·)` | 超界质量全部堆在 `cap` 这一个点上 |
| 重抽 | 遇到超界就重新抽 U | 直接把尾部削掉 |

为什么重抽破坏恒等式：恒等式要求 `P(X ≥ m)·m = RTP` 对所有关心的 m 成立。
clamp 时超界质量堆在 `cap`，而 `cap` 本身就在每个 m 的赢面内，恒等式不被破坏。
重抽则把这团质量直接删除，且 m 越接近 cap 被削得越狠。

实测（RTP=0.97、cap=120、100 万局）：

| 截断方式 | P(X≥10) 误差 | P(X≥30) | P(X≥100) |
|---|---|---|---|
| clamp 到 120 | +0.54% | −0.49% | **−2.85%** |
| 超界重抽 | −8.1% | −25.2% | **−83.2%** |

#### ③ 定点量化用 `floor` 不用 `round`

倍率保留 2 位小数。`floor` 把连续值**向下**取到分，于是 `P(X ≥ m)` 严格
**≥** `RTP/m`。`round` 会把一半质量抬到 m 的正上方，使 `P(X ≥ m)` 略**低于**
`RTP/m`。

实测 100 万局最大相对误差：`floor` −0.99% @ m=100 vs `round` +0.73% @ m=100。
两者同量级，但 `floor` 的偏差方向**单调**（只会偏低），永远不会把高逃跑点说成
更划算——这让单向断言更安全。

#### ④ 瞬爆概率的正确公式是 `1 − RTP/1.01`

`1.00x`（0 毫秒飞行、立即爆炸）在样本里就是「X 恰好等于 1.00」。因为有 `floor`
量化，这个事件的精确条件是：

```
floor(RTP/U × 100) ≤ 100  ⇔  RTP/U < 1.01  ⇔  U > RTP/1.01
```

`U` 在 (0,1) 上均匀分布，所以：

```
P(X = 1.00) = 1 − RTP/1.01
```

**RTP=0.87 时是 13.86%，而 `1 − RTP` 给的是 13.00%——差 0.86 个百分点。**
写验收断言时用错公式、又恰好把容差放宽到 0.02，这个偏差就会被长期藏住（见
第 2 节错误 #2）。

**推论：瞬爆概率不是可调参数。** 它由 RTP 唯一决定，RTP 越低瞬爆越多。想降
瞬爆只有抬 RTP 这一条路。

> 换 RTP 时恒等式依然成立，但具体数字要重跑

> 重新测。**不要拿这张表当当前配置的验收依据。**

实测（RTP=0.87、cap=1000、200 万局）对 `P(X≥m)·m = RTP` 的验证：

```
  m        P(X≥m)实测   RTP/m理论     偏差       c·S(c)
```

### 1.5 只有一种赔率模式

`odds_mode=9` 是唯一有效的值。模式 1–8（五段加权、百分比分布表、池子反推、
Jev AI 选段等）已全部删除，`decideRate()` 现在只剩一行：

```js
function decideRate(cfg, pot, pool, event, ctx) {
  void pot; void pool; void ctx;      // 历史签名，engine 按位置传 5 个参数
  return powerlawDecide(cfg, event && typeof event === 'object' ? event : null);
}
```

`pot` / `pool` / `ctx` 是**历史参数，读都不读**。读它们就让分布耦合到房间
状态上，回到第 0 节那个致命结构上。保留位置是为了让 `engine.js` 一行不用改。

判定 `S(m) = P(X ≥ m)` 用 `≥` 还是 `>` 需要注意：引擎的逃跑守卫是
`if (cur >= boom) return {code:10010}`——倍率恰好等于爆点时爆炸也已经在发生，
所以玩家赢在 m 需要 **X 严格大于 m**，真实胜率是 `P(X > m)`。

**这与恒等式用的 `≥` 不等价**，因为 `floor` 量化让每个 m 上都有一小团
`P(X = m) > 0` 的质量，落在「≥」的赢面内、不在「>」的赢面内。实测方向：

```
逃跑点m    P(X≥m)     P(X>m)     EV(用≥)     EV(用>)
   1.10x   79.0933%   78.3783%   -15.607%   -16.370%   ↓压低
    2.0x   43.5103%   43.2937%   -15.590%   -16.010%   ↓压低
  1000.0x    0.0829%    0.0000%   -19.635%  -100.000%   ↓压低
```

量化**恒定**把质量从「赢」挪到「输」，方向永远是压低玩家，偏移量可闭式预测
（`Δ = 0.97·m·P(X=m)`）。⇒ **定点量化不会制造正向尖峰**。但验收时
「全网格 EV > 0 的点数 = 0」这条**必须用 `>` 那一支**来断言。

**触顶局是一个特例**：cap 上的质量全部并进 `cap.00` 这一个点，而守卫是 `>=`
拒绝，所以**逃 cap 的胜率恒为 0、必输**（上表 1000x 那行）。这不是缺陷，是
clamp 截断设计的直接后果，对玩家单向不利，量级 0.087%。但它否定了「对外宣传
最高 1000 倍」这句话。

### 1.6 活动时段：只加 RTP，不换引擎

命中 `events_json` 时，幂律分支只做 `RTP += rtp_bonus`（clamp 到 `RTP_MAX`），
**不换引擎、不改 min/max**。换引擎等于让玩家识别出「这段时间的爆点不一样」，
而那正是要消除的可辨识信号。

因为抬 RTP 只是把整条 EV 线**平行上移**（第 1.1 节的 `m` 约掉了），所以
「不存在更好的逃跑点」这条性质在活动期间同样成立。

⚠️ **两条活动路径会叠加**：`act.rtpOverride`（`engine.js`）直接改写
`cfg.powerlaw_rtp`，`event.rtp_bonus`（`game-logic.js`）在 `powerlawDecide` 内
做加法。两者不在同一层，同时配置会相加。实测（base 0.87）：

```
只走 rtpOverride=0.90        → 0.90
只走 rtp_bonus=0.03           → 0.90
两条都配 (0.90 + 0.03)        → 0.93   ← 叠加
0.98 + 0.20 = 1.18            → 1.00   ← 硬 clamp 守住保本线
```

数学安全，但**配活动时二选一**，优先 `rtp_bonus`。

**配置饱和提醒**：`RTP_MAX = 1.00`。如果 base RTP 配到 1.00，**任何活动加成
都会被 clamp 吃掉，恒等于 0**，高倍活动不会有任何可见效果。实测：

```
base=1.00 bonus=0.03 → min(1.00, 1.03) = 1.00   实际加成 = 0.00
base=1.00 bonus=0.20 → min(1.00, 1.20) = 1.00   实际加成 = 0.00
```

此时玩家净 EV 仍是 `0.97 × 1.00 − 1 = −3.00%`，**仍是负期望**——RTP=1.00 只是
把庄家优势压到抽水的 3%，不是「玩家不亏」。

## 2. 错误经历

以下每条都是本项目真实发生过的。格式是「错在哪 → 怎么发现的 → 正确做法」。

### 错误 #1：循环论证测出的假数字

**错在哪。** 有两处报告声称「倍率涨幅 6%」和「≥100x 真实涨幅 22.91%」。
两个都是用「目标倍率 × 1.06」当作 `rateAt()` 的**输入**，再把输出当成实测涨幅。
这是在用被测函数自己的输出验证它自己。

**怎么发现的。** 改成让 `elapsed` 真实推进 100ms（`rateAt(100)` 对
`rateAt(0)`），涨幅远小于 6%，而且**随倍率递减**：1.62%（低倍率）→ 0.18%
（1000x）。逐点测下来根本没有一个恒定的 6%。

**正确做法。**

```js
// 错：把自己的输出当输入
const inflated = rateAt(rateAt(0) * 1.06, SCALE) / rateAt(0);

// 对：让时间真实推进
const real = rateAt(100, SCALE) / rateAt(0, SCALE);
```

**教训：验证一个函数时，不要把它自己的输出当输入再喂回去。** 构造测试输入时，
输入必须来自**独立于被测对象**的量（时间、坐标、用户输入）。

### 错误 #2：测试一直绿，但报数是错的

**错在哪。** `test/odds-powerlaw.js` 断言「瞬爆率 ≈ `1 − RTP`」，容差写
`0.02`（2 个百分点）。而正确公式是 `1 − RTP/1.01`，两者差约 0.9 个百分点：

```
RTP=0.87   精确 13.86%   错误 13.00%   差 0.86pp
RTP=0.90   精确 10.89%   错误 10.00%   差 0.89pp
```

这个偏差**正好落在容差里**。于是这条断言**从来不会红**，但它打印出来的数字
是错的，而且会一代一代传下去。注意这个偏差**不随 RTP 变化**——它约等于
`RTP × 0.0099`，所以换任何 RTP 值都会重现。

**怎么发现的。** 直接把概率算出来：瞬爆事件是「X 恰好等于 1.00」，条件是
`U > RTP/1.01`，所以概率是 `1 − RTP/1.01`。实测 100 万局 13.92% vs 精确值
13.86%，而 `1 − RTP` 是 13.00%——差得太明显，不可能是噪声。

**正确做法。** 把理论值换成闭式解，容差收紧到采样噪声量级：

```js
const BOOM_THEORY = 1 - RTP / 1.01;
ok(Math.abs(inst - BOOM_THEORY) < 0.005, ...);   // 0.005 = 0.5pp
```

**教训：容差太宽的测试会把系统性偏差训练成「已知噪声」。** 写容差要从
binomial 标准误 `σ = √(N·p(1−p))` 反算，而不是取一个「看起来够宽」的整数。
**测试绿只证明「没有超出我设的容差」，不证明「我设的容差是对的」。**

### 错误 #3：删导出时漏清引用

**错在哪。** 删除赔率模式 1–8 时把 `tableRate` 删了，但文件里还有多处引用。
后台的百分比分布表链一打开就抛 `undefined is not a function`。

**怎么发现的。** 功能测试跑不通，grep 找到残留引用。

**正确做法。** 删任何导出前，**先 grep 全仓引用再删**，范围要包含：

```bash
grep -rn 'tableRate' --include='*.js' --include='*.html' --include='*.md' .
```

```
admin/index.html:1327   // 实时预览：与服务端 tableRate() 完全一致的抽样逻辑
                       ↑ 注释指向已删除的函数；它所在的 w6Preview 面板属于
                         已删除的 mode 6，是一段永远不会被触发的死代码
server/db.js:403,406    // 历史记录注释，说明「当初没用 6」——这处是合理的

```

**`admin/index.html` 那处说明死代码比过期注释更危险**：注释说「与服务端
`tableRate()` 完全一致」，而那个函数已经不存在了。任何人照着这条注释去核对
两个实现的一致性，都会发现对不上。删模式时要连带删掉对应的 UI 面板与预览逻辑，
而不只是服务端分支。

### 错误 #4：照抄参考实现的注释，结论是反的

**错在哪。** 下注区改版给滑块的 `width` 加了 `transition: width .05s linear`，
抄的是参考实现的写法，注释里还写着「跟手拖动时几乎无延迟感」。**结论是反
的**：给 `width` 加 transition 后，拖动过程中每一帧都在追赶目标值，手感变黏。

**怎么发现的。** 实际拖动对比。有 transition 时填充层落后于手指，无 transition
时逐帧重设 `width`，视觉上是即时跟手。

**正确做法。** 只对**颜色 / 阴影**等视觉属性加 transition，**几何属性
（`width` / `height` / `transform`）不要加**——它们每一帧都在变，加了过渡
就等于引入滞后。

**教训：参考实现的注释也要验证，不能照抄。** 参考代码的注释描述的是**它那个
上下文**的行为，抄到新上下文里可能完全相反。「看起来很专业的注释」是最危险
的输入，因为它降低了你的警惕。

### 错误 #5：拖拽的 move 事件绑在元素上而不是 window

**错在哪。** `touchmove` 绑在滑块元素上。手指滑出窄条边界就停止触发事件，
填充层卡在半路不动。

**怎么发现的。** 手指快速划过边界时填充层冻结。

**正确做法。**

```js
el.addEventListener('touchstart', onStart, { passive: true });
window.addEventListener('touchmove',   onMove, { passive: true });
window.addEventListener('touchend',    onEnd,  { passive: true });
```

监听器在 `onEnd` 里解绑，否则每次触摸都泄漏一组监听器。

**教训：拖拽类交互的 `move` / `end` 事件一律绑 `window`。** 指针捕获
（`setPointerCapture`）是另一条路，但同样要处理「指针移出视口」的情况。

### 错误 #6：把「我的错误」升级成「系统的事实」

**错在哪。** 跑迁移脚本时传了一个错的库路径，得到 `unable to open database
file`，于是报告「本地库不存在，是空库，之前守恒测试的 130 万余额是自己造的」。

**怎么发现的。** 被质疑后重跑，脚本正常工作。**真库在 `E:\爆点\data\baodian.db`**
（13 张表、rounds 3085 行、users 20 个、用户总余额 1308276.47、最近写入
2026-09-30 21:41）——正是那个「空库产物」数字，它是真的。

**根因。** `db.js` 里库路径是 `path.join(__dirname, '..', '..', 'data',
'baodian.db')`。`__dirname` 是 `<repo>/server`，上溯**两级**到 `<repo>` 的
**父目录**，所以库在 `baodian/` 的**上一级**。我传了 `E:/爆点/baodian/data/…`，
多写了一层。

更严重的是：这个事实**本来就写在 `scripts/test-money-conservation.js` 的注释
里**——我读过那个文件、跑出了那个数字，然后**自己另拼了一个错误路径**，拿到
报错就下结论。

**正确做法。**

```bash
# 拿到「无法打开」的结论后，先分清是路径错还是库空
ls -la <可能的路径>                      # 文件在不在
node -e "new (require('node:sqlite').DatabaseSync)(p,{readOnly:true})" # 能不能读
node -e "... SELECT COUNT(*) FROM rounds"   # 有没有历史数据
```

「报错了」和「环境坏了」是两个不同的结论，中间需要证据。

**教训：报错先怀疑自己的输入，不要先断定环境坏了。** 更具体地说：**不要在
没有验证的情况下把一次失败的执行上升成关于系统的论断。** 一旦这么做了，下一
个人照着这个假结论排查会走错路，而纠正的成本比当初多打一行路径要高。

### 错误 #7：回归闸抄了实现而不是读源码

**错在哪。** 有一个回归测试把 `bindSlider()` 的实现**抄进测试文件**。副本与
源码各自演化，测试跑的是一个**不存在的函数**。更糟的是：副本里的桩函数返回
`null`，而断言恰好只检查「不抛异常」，所以**它是绿的**。

**怎么发现的。** 某个修复在源码里生效了，但测试仍然全绿——因为测试根本没在
测那份源码。

**正确做法。** 测试必须**读磁盘上的真实代码**：

```js
// 错：把实现抄进来
function bindSliderCopy() { /* 抄的 */ }

// 对：读真实文件 / 引入真实模块
const src = fs.readFileSync('public/js/app.js', 'utf8');
require('../public/js/app.js');   // 或直接测抽出来的纯函数
```

**教训：测试必须读磁盘上的真实代码。** 「我照着实现写了一份」和「我测了实现」
是两个完全不同的事——前者测的是测试文件自己。

### 错误 #8：推送后必须逐文件校验字节数

**错在哪。** `scp` / 连续 `ssh` 连接被远端主机掐断，导致**部分文件传输失败**，
线上 `app.js` 变成了「新版 HTML + 旧版 JS」的混合文件。残留的
`$('#betAmt').addEventListener` 指向一个已被删除的元素 → 脚本抛异常 → 整个
界面全黑。而**服务端日志是干净的**，因为异常发生在浏览器里。

**怎么发现的。** 打开页面全黑 + 服务端无异常 → 想到「文件没更新成功」→ 对比
文件内容发现版本混合。

**正确做法。**

```bash
# 推送后逐文件校验，不要只看 HTTP 200
scp -v <file> host:/path/ 2>&1 | grep -E "bytes|sent"
wc -c <local-file>            # 本地字节数
ssh host 'wc -c /path/<file>'  # 远端字节数 —— 必须相等
grep -c '<new-symbol>' <远端文件>   # 目标内容真的在
```

**静态文件是每次请求都重读的**，所以「服务端返回的是新内容」与「用户浏览器
加载的是新内容」是两个独立的端，必须分别验证。

**教训：推送后必须逐文件校验字节数。** 主机会掐断连续 ssh/scp 连接，这会让
「传输成功」这个假设不成立。**一次 200 和一个绿测试都不能证明部署是完整的。**

### 错误 #9：测试全绿不等于线上生效

**错在哪。** 出厂默认值断言（读 `POWERLAW.RTP_DEFAULT` 等**代码常量**）
可以 37/37 全绿，而线上 `settings` 表里是另一个值。两者可以同时成立。

因为 `seedSettings()` 只在**键不存在**时写入，而线上库这几个键都存在，所以
改了代码常量**永远不会**补写进已有安装。

实测（这是**两个不同时刻**的快照，正好演示「它会过期」）：

```
时刻 A                      代码常量   settings 表
  powerlaw_rtp                0.87         0.85     ← 不一致
  powerlaw_cap                1000         1000     ✅
  odds_mode                   —            9        ✅ 幂律已切

时刻 B（默认 RTP 改过之后）  代码常量   settings 表
  powerlaw_rtp                0.90         0.85     ← 仍然不一致
  powerlaw_cap                1000         1000     ✅
```

**注意时刻 B：代码常量改了两次，settings 表纹丝不动。** 这正是这个缺陷的
要害——`seedSettings()` 只在**键不存在**时写入，所以无论你改多少次常量、
重启多少次服务，已有的键都不会被覆盖。**只有迁移脚本能改它。**

**怎么发现的。** 写了一个把「代码常量」和「settings 表」并排读出来对照的
脚本。§6 全绿的同时它报红。

**正确做法。** 部署验证必须**有一个直接读 settings 表的检查**，不能只靠
默认值断言，也不能只靠后台面板显示（面板也读配置）。

```bash
node scripts/test-green-is-not-live.js    # 迁移前红，迁移后三行「一致 / 幂律 9」
```

**教训：永远不要把「默认值断言全绿」当部署成功证据。** 它验的是代码常量，
决定玩家体验的是 settings 表。两个来源必须对得上。

## 3. 后续如何避免

### 3.1 上线前验收判据清单

全部跑在**生产引擎自己的输出**上（`require('../server/game-logic.js')` 的
`powerlawRate`），不是自己的复刻。

```bash
node scripts/odds-final-report.js --rtp=<RTP> --cap=1000 --n=2000000 --rounds=1000
```

| 判据 | 阈值 | 怎么测 | 抓什么问题 |
|---|---|---|---|
| 净 EV 全网格极差 | 逐点判，见下 | 454 点网格（1.01→1000，对数加密） | 存在「某个逃跑点期望更高」的套利区 |
| 超 3σ 的点数 | = 0 | 逐点 `\|ev − theory\| ≤ 3σ` | 分布形状被某个机制挖掉 |
| 净 EV > 0 的点数 | = 0 | 用 `P(X>m)`（引擎真实判胜规则） | 确定性套利区 |
| 空档数 | = 0 | 细网格上 `S(c)` 有无平台段 | 玩家看得见的「习惯区间」边界 |
| 相邻相关系数 \|r\| | < 0.01 | 200 万局相邻两两相关 | 存在逐局记忆（房间不变→分布不变） |
| 非配额 | 每 100 局「≥10x」局数标准差 > 1.5 | 分 100 局块统计 | 配额式尖峰（可被玩家反推） |
| 短周期 | 无 | 2000 局序列检查周期 2/3/4/5/7/10/20/50/100 | 循环序列 |
| 上下界 | 全部 ∈ [1.00, cap] | min/max | NaN / Infinity |
| 随机源 | `Math.random()` 调用 0 次 | 打桩计数 | 随机源可预测 |
| **尾部可达性** | 见 3.2 | `≥N` 计数 / p99 / 观测最大值 vs 配置上限 | 「配了 1000 但实际只出 20」 |
| **代码常量 vs settings 表** | 三行全「一致」 | `scripts/test-green-is-not-live.js` | 测试全绿但线上没生效 |

### 3.2 三个判据的判法要点

**① 判 EV 必须逐点判 3σ，不能判极差。** n 行各自的估计误差都是 σ 量级，取
最大最小必然把两个各自 1.2σ 的误差拼成 2.4σ —— **n 越多极差越大，分布越完美
反而越会「报警」**。实测 RTP=0.87/cap=1000/N=200 万：逐行最大偏差 1.55σ，
而极差 3.27pp 全部来自尾部。

σ 的公式（**分母里的 `/N` 不能漏**，漏了会让 3σ 放大 N 倍，200 万局时是
200 万倍，于是**所有判据永远通过**——那才是危险的那种绿）：

```js
const sigma = c * (1 - EDGE) * Math.sqrt(P * (1 - P) / N);
```

**② 尾部必须标注样本不足。** 尾部点的 σ 本身就有几个百分点，在那个分辨率下
「偏差 > 3σ」不是性质结论。实测 RTP=1.00/cap=1000：

```
  c      P(X≥c)理论   N=100万命中   3σ相对误差   所需 N
100x        1.0000%       10000       2.98%     9.0e+6
500x        0.2000%        2000       6.70%     4.5e+7
865.2x      0.1156%        1156       8.82%     7.8e+7
1000x       0.1000%        1000       9.48%     9.0e+7
```

`scripts/odds-final-report.js` 已内建这个闸：3σ 相对误差 > 3% 的点会单独列出
并标注所需样本量，**不计入 `maxZ` / 超标点计数**。

**③ 阈值可达性必须测尾巴，不能测均值或「没超过上限」。** 「没有溢出」是关于
**钳制**的陈述，不是关于**范围**的陈述——一个组件可能完全不产出接近上限的值，
于是得到一个完美的「无溢出」结果。有效判据是：尾部 `≥N` 计数、p99、观测最大值
vs 配置上限。`test/odds-powerlaw.js` §6 已把 `≥125x` 与 `≥500x` 钉成断言。

### 3.3 随机算法只能断言不变量，绝不断言具体数值

幂律把 20% 的概率质量压在 1.00–1.10 这 10 个分值上，所以**碰撞是正确形态**。
断言「200 局里不同值 > 150 个」会随机红，而且会训练你不断放宽阈值直到它
失去意义。

要断言的**不变量**：

- 无周期性（任何短周期都不成立）
- 整体样本的 `P(X ≥ m)` 仍等于 `RTP/m`（性质，不是某几个值）
- 上下界不越界
- 相邻局相关系数 ≈ 0
- 分布形状不出现「某档为 0」（空档）

不要断言的：**任何具体的倍率值、具体的分位数、具体的不同值个数。**

### 3.4 删导出 / 改签名前的 grep 清单

```bash
# 全仓引用，含测试、注释、前端内联脚本
grep -rn '<函数名>' --include='*.js' --include='*.html' --include='*.md' .

# CommonJS / ESM 两种导出都要查
grep -rn "require.*<模块>\|from '.*<模块>'" .

# 改函数签名：查所有调用点（参数个数/顺序变了不会报错，只会静默传错）
grep -rn '<函数名>(' --include='*.js' .
```

**注释里的引用也要清。** 它们会在下次有人 grep 时造成误导。

### 3.5 目录结构与新赔率模式的上线顺序

引擎导出（`server/game-logic.js` 末尾）：`CFG` / `FLIGHT_SCALE` / `flightMs` /
`rateAt` / `decideRate` / `activeEvent` / `payout` / `round2` / `sleep` /
`powerlawRate` / `powerlawDecide` / `powerlawReport` / `normRtp` / `normCap` /
`normEventBonus` / `POWERLAW`。

**任何行为变化都必须是「参数」而不是「代码」** —— 行为输入要么是 `cfg`
（`refreshSettings()` 每局重读，不缓存），要么是常数。否则运营改一个配置
就可能要改代码，而代码没同步就静默失效。

**新增 / 修改赔率模式的上线顺序（顺序反了配置不生效且不报错）：**

```bash

node scripts/migrate-powerlaw.js --apply --force # 写入并切到幂律 9

# 2. 重启服务（必须！否则进程读到的是旧配置）
#    注意：本项目已删除进程内 memo 缓存，refreshSettings() 每局重读，
#    所以「重启才生效」不再是配置缓存问题，但 migrate 脚本的提示仍保留。

# 3. 验证（两个来源必须对得上）
node scripts/test-green-is-not-live.js    # ← 必须绿
node scripts/odds-final-report.js --rtp=<线上实际值> --cap=1000 --n=2000000
```

⚠️ **第 3 步的第一个命令不能省。** 它是唯一能直接读出 settings 表实际值的
检查。默认值断言和后台面板**都读配置默认值**，不能替代它。

### 3.6 前端资源版本号（不属于赔率，但同属部署完整性）

任何前端资源变更后，**四类资源全量** bump `?v=N`（HTML / CSS / 主 JS / vendor）：

```bash
grep -oE '\?v=[0-9]+' public/index.html | sort -u    # 确认版本唯一
git show HEAD~1 -- public/index.html | grep -oE '\?v=[0-9]+'   # 确认版本真的动了
curl -s -I "https://host/js/app.js?v=<新>" | grep -iE '^HTTP|cf-cache-status'
curl -s "https://host/js/app.js?v=<新>" | grep -c '<新符号>'   # 0 = 还是旧的
```

**一个 200 只能证明 CDN 上「有东西」，不能证明「是你的字节」。** 真正的警报
是 `cf-cache-status: HIT` **打在新版本号上**——说明 bump 没生效。

### 3.7 删掉的旧套件

`test/odds-weighted.js` 测的是**已被删除的赔率模式**（它硬编码
`odds_mode: '5'`），现在必然红。**不要为了 suite 全绿去改断言迎合新行为** —— 它
测的东西不存在了，正确做法是删掉它。`test/odds-table.js` 同理（它有一条断言
在检验「活动分支覆盖分布表」，那是旧模式时代的语义）。

**关于随机种子。** 引擎用 `crypto.randomBytes`（CSPRNG），**没有可复现种子**。
所以复现靠**样本量**而不是靠 seed：同一条判据跑两次，结论应当一致；判据的
容差就是按这个噪声水平设的。`scripts/` 下所有脚本同样不提供 seed 参数。

## 5. 一页速查

```
赔率分布     X = min(cap, max(1.00, floor(RTP / U)))     U ~ Uniform(0,1), CSPRNG
核心恒等式   P(X ≥ m) · m = RTP          ⇒  玩家净 EV = 0.97·RTP − 1（与 m 无关）
引擎判胜     X > m   （守卫 cur >= boom 拒绝）—— 与恒等式用的 ≥ 不等价
瞬爆概率     1 − RTP/1.01      不是 1 − RTP
飞行时长     t = (√(40r − 24) − 4)/2  × 2.5 秒    100x 以上对数线性加速
随机源       crypto.randomBytes(6)        Math.random 禁用（xorshift128+ 可被预测）
赔率模式     odds_mode = 9（唯一）        模式 1–8 已删除
活动         只加 RTP（rtp_bonus），不换引擎    两条路径会叠加，二选一
饱和提醒     base RTP = 1.00 时活动加成恒为 0（clamp 吃满）   玩家净 EV 仍 −3.00%
上线三步     改库 → 重启 → node scripts/test-green-is-not-live.js（必须绿）
```

```
验收判据     逐点 |ev − theory| ≤ 3σ（不判极差）    超 3σ 点数 = 0
             净 EV > 0 点数 = 0（用 P(X>m)）      空档 = 0
             |r| < 0.01    非配额（标准差 > 1.5）  尾部 ≥N/p99/最大可达
             尾部点须标注样本不足（3σ 相对误差 > 3% 即不可作判据）
```
